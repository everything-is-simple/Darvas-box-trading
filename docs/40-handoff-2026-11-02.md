#### 1.1.3 07:20 定性尝试：曾判为「入站按程序路径白名单」——**已被 §1.1.4 推翻，勿引用本条结论**

用户关闭 Clash Verge 的 TUN 模式后重跑 `go test ./internal/gui -run TestAPIEndpoints -v`：**仍失败**（同签名）。
我（智能体，沙箱外）在 TUN 关闭后立即做了判定矩阵，结论彻底钉死：

| 实验（全部沙箱外、TUN 已关） | 结果 |
|---|---|
| Python 新建 `127.0.0.1` 监听 → 自连 | **OK** |
| Python 绑本机 IP（192.168.3.4）监听 → 自连 | **OK** |
| Python 绑 `0.0.0.0` 监听 → 回连 | **OK** |
| **Go 编译的 exe 作服务端** → Python 连 | **超时（丢 SYN）** |
| Python 作服务端 → **Go exe 作客户端** | **OK** |
| **把 `python.exe` 复制成 `copy_py.exe` 后作服务端** → 自连 | **超时** |

三条判据：
1. **不是语言问题**：同一个 Go exe **作客户端完全正常**（能拉到 Python 服务端的响应），只有**作服务端**被丢 SYN。
2. **不是 TUN 层**：TUN 关闭后回环在本进程中已完全恢复（Python 三种绑定全通），但 Go 服务端仍不通 → TUN 只是叠加的第一层。
3. **是按程序路径**：`python.exe` 原路径放行、**改名复制后立刻被拦**——同一份二进制、同一行为，只有路径变了。

**归因**：Windows Defender 防火墙的「允许应用通过防火墙」**按完整程序路径**生效。
现有允许规则里确有 WorkBuddy 内置 `...\workbuddy\resources\vendor\python\python.exe`（两条），
而**没有任何 Go 相关条目**；`go test` 每次把测试二进制生成到新的 `%TEMP%\go-build*\b001\gui.test.exe`，
天生不可能在名单里。已存活能连的 7897（verge-mihomo）/ 4709（wpscloudsvr）也都是安装期写过规则的程序。

**定性结论（T1 最终）**：`TestAPIEndpoints` 失败**是机器环境问题，代码无罪**。
任何「无防火墙入站允许规则」的新进程在本机监听回环，都会被静默丢 SYN；`httptest` 因此必然超时。
**不要再为此改代码。**

**解法（需管理员，二选一）**：
- **A. 固定路径 + 一条规则（推荐，一次性）**：
  ```powershell
  # 管理员 PowerShell
  cd I:\Darvas-box-trading
  $env:PATH = "I:\tools\go\bin;" + $env:PATH
  go test -c -o I:\Darvas-box-trading\var\tmp\gui.test.exe ./internal/gui
  New-NetFirewallRule -DisplayName "Darvas GUI Test (loopback inbound)" -Direction Inbound `
    -Program "I:\Darvas-box-trading\var\tmp\gui.test.exe" -Action Allow -Profile Any
  cd I:\Darvas-box-trading\var\tmp ; .\gui.test.exe -test.run TestAPIEndpoints -v
  ```
  之后每次改代码只需重新 `go test -c -o var\tmp\gui.test.exe ./internal/gui` 再跑该 exe，规则长期有效。
- **B. 临时验证（只判定、不留痕）**：管理员执行
  `Set-NetFirewallProfile -Profile Domain,Private,Public -Enabled False` → 跑 `go test` → **立刻**
  改回 `-Enabled True`。若关了能过，则归因确认无误。

#### 1.1.4 07:35 复测全绿：T1 正式关闭 —— 根因是 **TUN 过滤残留**，§1.1.3 归因作废

用户以**管理员**身份跑 `var\tmp\gui.test.exe -test.run=TestAPIEndpoints`，脚本设计为「防火墙开启时先跑一次基线」，
结果：**`EXITCODE_FW_ON=0`（PASS）**——**防火墙三档全开的状态下测试就过了**，直接否掉防火墙假设。

随后补两刀把变量彻底分开：

| 复测（07:33–07:37） | 权限 | 路径 | 结果 |
|---|---|---|---|
| `var\tmp\gui.test.exe`（用户手动，管理员） | 管理员 | 固定 | **PASS**（防火墙全开） |
| `var\tmp\gui.test.exe`（智能体执行） | 普通 | 固定 | **PASS** |
| `go test ./internal/gui -run TestAPIEndpoints -v` | 普通 | `%TEMP%\go-build*` | **PASS** |
| `go test ./internal/...` 全量 | 普通 | — | **18 个包全 ok，含 `internal/gui` 1.049s** |

**真正的根因**：Mihomo TUN 的 WFP 过滤规则在「关掉 TUN」之后**并不会立即卸载**，存在分钟级残留（07:09 关、07:16 仍失败、
07:33 已恢复，约 15–20 分钟；另一可能是脚本里 `Set-NetFirewallProfile off→on` 重建了过滤引擎、顺手清掉了残留规则）。
在残留窗口内，规则按**进程**分流：命中白名单的（`python.exe`）回环正常，未命中的（Go 测试 exe、`copy_py.exe`）SYN 被 TUN 栈吃掉。

**§1.1.3 错在哪**：它把「同一时刻、不同 exe 的横向对照」当成因果，得出「防火墙按程序路径白名单」的结论。
正确的判定必须是「**同一个 exe 的前后纵向对照**」——本次正是靠「同一份 `gui.test.exe`，先管理员/FW 全开 PASS、再普通权限 PASS」
一步推翻。这条要作为环境类排查的标准动作：**变量没分离干净之前，不做机制归因。**

**T1 最终裁定**：`internal/gui.TestAPIEndpoints` **本身没有缺陷**，三份审计的「发布阻断项」**作废关闭**。
测试基线（2026-11-02 07:37）：`go test ./internal/...` **18/18 全绿**。
以后若再出现该测试超时，先查是否有 TUN/代理软件刚切换过模式，**等待规则卸载或重启该软件后再复测**，不要动代码。
