1. **基线 = 49 键**，定义是「`internal/` 与 `cmd/` 里 `GetFloat/GetInt/GetString` 实际读取的全部 param 键」。

   从此基线**可从库里直接读出**，不再依赖「代码默认恰好等于实验结论」。

   （A 判据已不决定仓位单位，仅作第 10 维归因原料）、`tdx.root`（机器相关路径，**不该入库**）。

## 五、参数层踩过的坑（可复用教训）

1. **0017：种子给了 `max_hold=7`，代码默认 0 变死代码**——沿用 7 个月的「事实基线」其实是种子值，
   代码默认早就没人走过。教训：**种子即事实**，改默认必须写 migration。
2. **0019 误杀 `tdx.root`**：0019 声称清理「29 个死参数」，实际 **28 个真死 + 1 个活参数**
   （`tdx.root` 代码仍在读）。若照旧库直接跑新 exe，迁移会删掉本机 `D:\new_tdx64` 的设置，
   默认值又写死老机 `H:/new_tdx64` → **每日 ingest 静默失效**。
   已修：`tdxRoot()` 改为「环境变量 > 参数 > 自动探测 D:/H:/I:」，本机不再依赖参数行。
3. **三个口径打架**（26 / 38 / 39 / 47 / 48 / 49）：根因是「谁在数种子、谁在数快照、谁在数代码」。
   教训：**参数清单必须由代码反推**，人力维护的表一定会漂。0030 加 `pos.regime_scale.mode` 后
   代码实读口径 47→48；0031 把 `pool.blacklist_months` 从直读 SQL 改走 `GetInt` 三件套口径后 48→49。
4. **0019 第二个误杀 `pool.blacklist_months`**：跟 `tdx.root` 同型——0019 声称清理死参数，
   实际 `repo_trade.go:applyTrackTransition` 仍在读它（定亏损清仓后的黑名单冷却月数）。
   0019 删行后代码走默认 12，恰等于 0017 种子值，**行为不变是纯运气**。
   更隐蔽的是：`param_ledger.py` 只扫 `Get*` 字面量，**直读 SQL 是盲区** → 台账漏登、
   `ParamRepo.Set` 对不存在的 key 静默成功、0027 指纹含/不含此行的库指纹不同（对账噪声）。
   已修：0031 重新种子化 `=12`，代码改走 `GetInt` 三件套口径，`Set` 加固 RowsAffected=0 报错。
5. **迁移写法不统一**：0001/0003/0010 用 `INSERT OR IGNORE`，0018 用裸 `INSERT`，0025/0026 用
   `ON CONFLICT DO UPDATE`。解析脚本必须区分三种语义，否则会漏掉 0018 那批种子。

## 六、参数自由度分类（原 `59`，2026-11-06 并入）

> **§二 记「值」，本节记「自由度」。** 两者是同一批键的两种切法，不存在跨文档冲突。
> 缘起：Chan 的 252× 规则算出「49 键 vs 上限 13.5」，但那是把**所有键都当自由度**，属过度指控。
> 本节按「这个键到底会不会改变成交」重新分类。

### 6.1 结论：49 键里只有 21 个是真参数，其中 16 个还活着

| 类别 | 数量 | 是否产生自由度 |
|---|---|---|
| A 常量（法定/环境/身份/成本假设/原著规定） | 10 | 否 |
| B 结构性开关（定义系统物种，on 在跑） | 2 | 否（开关已定案） |
| C 死键（功能已否决或未启用） | 7 | 否（不生效） |
| E 仅日志/归因（不参与成交） | 9 | 否 |
| **D1 已验锁定**（曾实验，已定案） | 5 | 理论是，实际冻结 |
| **D2 活的自由参数**（消参标的） | **16** | **是** |
| 合计 | 49 | — |

按 Chan 252× 上限（日频 13.5 / 笔数 4.5）：真实待调自由度 **16** → 超上限 **1.19 倍**；
加上已锁定 5 个 = 21 → 超 1.56 倍。**目标：D2 从 16 压到 9**，加 D1 的 5 个 = 14，落在 13.5 附近。

### 6.2 分类定义

| 类 | 判据 | 处理 |
|---|---|---|
| **A 常量** | 由法律、交易所、券商、机器环境、回放起点决定；改它等于改世界 | 保留，标注「事实」，永不做梯度实验 |
| **B 结构开关** | on/off 决定系统有没有这个模块，不是数值寻优 | 已定案，不再动；推翻须走否决流程 |
| **C 死键** | 值为「关闭/未启用」，代码路径不生效 | 删表行或删代码分支 |

| **D1 已验锁定** | 做过实验且有结论，冻结 | 保留但标 `frozen`，不计入自由度预算 |

### 6.3 ⛔ 唯一的真陷阱：`pos.equity_gate`

| 键 | 代码默认 | 库内生效 | 判定 |
|---|---|---|---|
| `pos.equity_gate` | **on** | **off** | **删键会让权益闸门自动打开，系统剧变** |

其余 38 个有库值的键，默认值与生效值完全一致（`param_ledger.py --json` 全量比对）。
另三个不一致但属故意：`pos.newhigh_ladder`（off→on）、`gate.ma60.mode`（off→stop）是 B 类核心开关；
`pool.max_hold`（0→14）是 D2 活参——都保留种子。

> 所以「删键」在参数表上只涉及 **C2 的 3 个 + C3 的 1 个 = 4 行**，删完 **42 → 38**（不是 49→40）。
> 库内只有 **42 键**，另 7 个（`buy.highest_box_mode`/`highest_box_window`/`uptrend_only`/`regime.a.*` 三键/`tdx.root`）从来不在表里。

**正确验收**：写一条单测，断言「param 表不含该键时，`ParamRepo.GetXxx` 返回的默认值 == 删除前的生效值」。
比回测便宜，且是确定性证明，不受行情影响。（旧写法"删键前后同库重跑比对成交序列"对 C2/C3 不成立——删的是表行，读的是默认。）
