## §0 一句话结论

**TdxQuant 能提供我们缺的「真实除权除息记录 + 复权因子」，但它不是给 Go 引擎直接喂数据的现成接口；它的价值在于补上「用价格跌幅反推除权」这个盲区，进而支撑「复权后继续持有」的实验，而不是取代我们现有的数据口径。**

## §1 背景：一个必须先说清的口径纠偏

### 1.1 之前的说法是错的，这里正式更正

> ~~「达瓦斯理论必须用原始价格跑」~~ —— **此说法不成立，予以撤回。**

真相是：**用原始价格是「没有可靠免费复权数据」这个现实约束下的无奈选择，不是理论偏好。** 用户明确：只要系统能拿到好复权数据、最终能实战，**就可以改**。本项目的目标不是守护某一个数据口径，而是「系统最终能实战」。

### 1.2 当前系统到底在用什么数据（以代码和 docs/01 为准）

| 项 | 现状 | 出处 |
|---|---|---|
| 灌库数据源 | **TDX 前复权日 K**（`{sh,sz}\lday\*.day`） | `docs/01` §10.1 第 291 行 |
| 复权跳空日处理 | 持仓股**强制清仓**（价=昨收×(1−滑点)，避开跳空损失） | `internal/match/match.go` §3.8，用户 2026-10-19 拍板 |
| 除权检测方式 | **用价格跌幅反推**：`close` 相对昨收跌幅超过涨跌停幅度即判除权（主板 9%、科创/创业 19%） | `match.go` `isDividendGap` |

**关键点**：系统**已经在用前复权价**，但「哪一天除权」是靠**价格跌幅反推**的，**没有查真实的除权除息记录**。这就是 TdxQuant 能补的盲区。

### 1.3 反推法带来的已知代价（2026-11-02 T3 实验实测）

097/2017 库中，复权强制清仓共 **12 笔，合计 +71,272**（平均 +5,939/笔），而策略出口当年合计 −100,721。也就是说：

- **这 12 笔清仓抵消了 2017 年策略出口亏损的 71%。**
- 它们不是策略赢了，而是「能分红送股的强势股，在除权日被硬砍在高点」——规则性缺口，不是 alpha。

这 12 笔里 top3：sh603357 +21,436、sh603800 +12,367、sh600828 +11,430。

## §2 TdxQuant 是什么

| 项 | 值 |
|---|---|
| 全称 | TdxQuant，通达信量化平台（深圳市财富趋势科技股份有限公司） |
| 定位 | 基于通达信金融终端的 **Python 量化策略运行框架**，API 形式提供行情数据 + 交易指令 |
| 文档 | `https://help.tdx.com.cn/quant/` |
| 语言 | Python 3.7–3.14（64 位），建议 3.13 |

### 2.1 两种运行模式（决定我们怎么用）

| 模式 | 依赖 | 适用场景 |
|---|---|---|
| **tqcenter** | 必须先启动通达信金融终端 / 专业研究 / 量化模拟版 / 期货通 | 需要客户端数据仓库时 |
| **tqserver（即 tdxaidata）** | **不依赖客户端**，独立服务 | **我们选这个**——不天天开通达信终端也能取数 |

### 2.2 它提供的复权相关数据（我们要的核心）

- **除权除息数据**（基本面数据类目下明确列出）
- **复权因子**
- **各种类型的复权后数据**（前复权 / 后复权 K 线）

即：**除权除息记录、复权因子、复权后行情**三层都有，比我们现在的「前复权价 + 价格反推」更完整、更可审计。

## §3 引入它，我们到底缺什么、补什么

### 3.1 我们缺的（真实缺口，非虚构）

1. **真实除权除息记录**：现在靠 `isDividendGap` 价格跌幅反推，存在三类风险——
   - **漏判**：除权幅度小于涨跌停阈值（小额分红/送股）→ 不会触发清仓，价格序列出现隐性跳空；
   - **误判**：单日真实暴跌超阈值但并非除权（如黑天鹅一字跌停、ST 摘帽等）→ 被当成除权清仓；
   - **不可审计**：反推没有「官方除权日」做对账锚。
2. **复权因子**：能让我们在「前复权价」与「原始价」之间精确换算，而不是依赖 TDX 客户端已算好的单一前复权序列。
3. **除权后继续持有的可能性**：要改引擎做「除权后按调整价继续持有」，必须先有准确的除权日 + 除权比例，反推法给不了。

### 3.2 引入后能补上什么

| 用途 | 具体内容 | 价值 |
|---|---|---|
| **校准除权检测** | 用真实除权除息日清单，对 `isDividendGap` 的漏判/误判做对账 | 把「反推」变成「查证」，消除 §3.1 的三类风险 |
| **支撑复权后继续持有（T7）** | 提供除权日 + 除权比例 + 复权因子，供引擎在除权日不砍仓、按调整价重算箱体与止损 | 直接针对 §1.3 的 +71,272 规则缺口 |

### 3.3 它**不**用来做什么（边界）

- **不取代回测主口径**：当前主口径是「前复权价 + 复权日清仓」，这是系统既定事实，TdxQuant 只补「除权记录」这一层，不推翻整套口径。
- **不重造一个回测引擎**：TdxQuant 自带回测，但我们有 Go 引擎 + 14 年历史校准 + 实验登记体系，**引擎不动**，只取它的数据。
- **不引入第二套交易通道**：实盘/模拟通道暂不碰，本方案只谈数据。

## §4 接入方案（分两阶段，先数据后引擎）

### 阶段一：数据校准（低风险，不动引擎）

目标：拿到「真实除权除息清单」，与现有 `sim:dividend` 清仓记录对账。

1. 用 `tqserver`（不依赖客户端）写一个 Python 抽取脚本；
2. 抽取**全市场除权除息记录 + 复权因子**，落成我们库能读的表（如 `dividend_events`）；
3. 跑一个**只读对账脚本**：把 `isDividendGap` 判定的除权日 vs 真实除权日逐日比对，输出漏判/误判清单；
4. 出报告：反推法的漏判率、误判率、以及这些偏差对 14 年账本的净影响。

**产出物**：一份「除权检测校准报告」，**不改任何交易逻辑**。

### 阶段二：复权后继续持有（T7，改引擎，须另立预注册）

目标：把「除权日强制清仓」改为「除权日按调整价继续持有」。

1. 引擎在除权日不砍仓，改用**复权因子**把持仓成本、箱体 top/bottom、止损价统一折算；
2. 箱体重算、止损上移逻辑照常；
3. 作为 **B 类单变量实验**：变量 = 「复权处理方式」{强制清仓 vs 继续持有}，其余参数 100% 复刻基线；
4. 年集、判定门槛、必报表沿用 `docs/29` 口径，单独预注册。

**这是策略决策，不是数据问题**——数据（除权记录）阶段一已备好，阶段二能否启动取决于是否立项。

| 本机 TDX | `D:\new_tdx64`（本机）/ `H:\new_tdx64`（老机）——是否「支持 TQ 策略功能」的版本，需实测确认 |

> **已查明的接口（2026-11-02 官方文档核实，来源见附 B）**：
>
> **① 复权 K 线 —— `get_market_data` 的 `dividend_type` 参数**（`tqserver.tqs` 与 `tqcenter.tq` 同名同参）
> ```python
> from tqserver import tqs
> data = tqs.get_market_data(
>     field_list=["Open","High","Low","Close","Volume","Amount"],
>     stock_list=["600000.SH"],      # 必须带 .SH/.SZ 后缀
>     period="1d",
>     start_time="20180101", end_time="20261231",
>     count=-1,                       # -1 = 拉全历史
>     dividend_type="front",          # none=不复权 / front=前复权 / back=后复权
>     fill_data=True,                 # 补全停牌缺失交易日
> )
> ```
>
> **② 除权除息记录 —— `get_divid_factors`**（`tqserver` 同样支持，官方确认在「tqserver 支持的 tqcenter 函数」清单内）
> ```python
> df = tqs.get_divid_factors("600000.SH", "", "")   # start/end 留空 = 全历史
> ```
> 返回 `pd.DataFrame`，索引 `Date`（除权除息日），列字段：
>
> | 字段 | 类型 | 含义 |
> |---|---|---|
> | `Type` | str | 类型：**1=除权除息** / 11=扩缩股 / 15=重新调整 |
> | `Bonus` | str | 红利（**每 10 股分红，元**） |
> | `AllotPrice` | str | 配股价 |
> | `ShareBonus` | str | 送股/扩缩股比例 |
> | `Allotment` | str | 配股 |
>
> > 注：接口只支持沪深京（A 股），与我们池子一致；`Bonus`/`ShareBonus` 是**每 10 股**口径，落库换算时须统一到「每股」再算复权因子，避免单位错位。
>
> **③ 关键确认：`tqserver` 不依赖客户端** —— 官方原文「直接通过调用 TdxAiData.dll 从服务器获取数据，不依赖本地数据、不依赖通达信策略运行环境」，且**不提供交易/公式/客户端交互功能**（这正是我们要的：只取数、不引交易通道）。

### §5.1 连通性验证结论（2026-11-02 实测，决策依据）

**最终结论：`tqserver` 通道已打通（升级客户端后 dll 加载 + 接口调用均成功），唯一卡点是鉴权——需要一个「数据服务 Key」，且按积分计费，不是免费匿名接口。**

| 探测项 | 结果 |
|---|---|
| 本机 TDX 目录 | `D:\new_tdx64`（**已升级**，含 `PYPlugins\TdxAiData.dll` + `PYPlugins\sys\tqserver.py`） |
| Python | 3.13.12（WorkBuddy 内置），pandas/numpy 已装 |
| `tqserver` import | `from tqserver import tqs` **成功** |
| `get_divid_factors("600519.SH")` | dll 调用成功，但返回 **`错误码 13「Need TokenKey, Check TdxAiData.in」`** → 空 DataFrame |
| `get_market_data` | 同样报 `错误码 13`，K 线返回空 |
| 根因 | `PYPlugins\TdxAiData.ini` 的 `[Token] token=` **为空** |

**三条硬结论：**

1. **`tqcenter`（旧模式）硬依赖运行中的客户端**——升级前实测 `InitConnect` 报 `ErrorId=11`。现已弃用该路径。

2. **`tqserver`（新模式）已可用，但需要鉴权 TokenKey**——`TdxAiData.ini` 注释原文：「token 请登录通达信个人版商城的会员中心 → 积分和Key管理 → 创建数据服务Key」。**这不是免费匿名接口。**

3. **计费方式：按积分消耗**（第三方实测交叉印证）——简单查询约 1 积分，复杂查询约 15 积分；新用户初始送 10,000 积分，每天签到 +100。对「一次性拉全历史除权除息清单」这种批量任务，积分消耗需要先估算。

**阶段一的真正前置（只需你做一步）：**
> 登录通达信 VIP 商城 `https://vip.tdx.com.cn/` → 会员中心 → 积分和 Key 管理 → 创建 Key（**勾选「通达信数据服务」类型**）→ 把 Key 填进 `D:\new_tdx64\PYPlugins\TdxAiData.ini` 的 `[Token] token=`。

> 填完 Key 后，`tqserver` 即可脱离客户端取数。这是「登录账号 + 生成 Key + 手填 ini」的操作，涉及你的账号凭证，**AI 不代做**；你填好后我再跑一次连通性实测确认打通，并估算批量拉取除权除息清单的积分成本。

## §6 决策门：现在不动引擎，先定「做不做」

引入 TdxQuant 本身**不是实验**，它只是「数据源」。真正要决策的是 §4 阶段二那个 B 类实验（复权后继续持有）。

在启动阶段二之前，必须先回答：

1. **「复权后继续持有」是不是我们想要的？** 它意味着放弃「复权日砍在高点」的确定性，承担除权后股价继续下跌的敞口——这是风险偏好，不是数据问题。
2. **优先级 vs 现有队列**：`docs/40` §2 还有 T4（SSoT 对账）/ T5（卖出出口分解）/ T6（raiseStops 事件研究）。阶段二插不插队，按 `docs/29` §四登记表裁定。

**阶段一（数据校准）风险极低、只读不改，建议先行**，因为无论阶段二做不做，校准结论都能消除 §3.1 的三类风险。
