## 二、重建 SOP（照做即可，不依赖记忆）

### 2.1 前置

1. 确认源库 = `var/bt/full_hist_10pct.db`（唯一历史行情库，11-02 已灌 59,665 条真实 `dividend_event`）。
2. 确认二进制 = `var/bt/darvas_base.exe`（同一二进制锚，HARD①：**跨机/跨二进制不可横比**）。
3. 确认磁盘：归档盘 = `B:/Darvas-archive`（A 盘已冻结只读）。`var/bt` 只放 base + full_hist + 当次实验。

### 2.2 重建命令（三种规模）

```bash
# 冒烟：单年（快速验证方向；跑出的库不跨年结转，仅供对账，不作正式基线）
python scripts/base_run.py --years 2007 --mirrors A

# 代表年（先看方向对不对；同样只是分年对账用）
python scripts/base_run.py --years 2007,2010,2013,2018 --mirrors A

# 正式重建：连续单库（阶段 C，判据见 §六；持仓跨年结转、真实复利，这才是基线本体）
python scripts/base_run.py --cont --from 2005-01-01 --to 2018-12-31 --mirrors A

# 中断后续跑（阶段 D，判据见 §六；resume 分支会校验参数冲突，改了参数须删库重建）
python scripts/base_run.py --cont --from 2005-01-01 --to 2018-12-31 --mirrors A --resume
```

> **口径（2026-11-04 修正）**：§五 目标态是**连续单库**，故正式重建命令已从 `--years`（单年模式，
> 每年 100 万起跑、不跨年结转）改为 `--cont`。单年模式仅保留为冒烟/分年对账用，**跑出的 14 个
> 单年库不是基线**，不能拿来做 V3/V4 判据——判据必须打在连续单库上。

**关键点**：
- `base_run.py` 已把 4 个实验结论注入项（`newhigh_ladder=on / ma60=stop / max_hold=14 / equity_gate=off`）
  写死在 `COMMON` 里，**与 migration 0025 一致**——所以重建**不需要再传 `--set`**，参数从库里直接读出。
- 执行器**幂等**：`db_complete()` 判 `equity_snapshot` 非空才跳过，强杀留下的半成品会被识别并删掉重跑。
- **串行，勿并发**（红线：回测并发会污染 scratch 心跳）。

### 2.3 耗时

实测 **28.4 min/年** × 14 年 ≈ **6.6 小时**。**只在白天跑**（夜间沙箱回收激进，长进程必被砍，见 MEMORY 运维坑）。

## 四、基线身份（F9 的补法）

**✅ 已落地（0027，2026-11-04，阶段 B）**：三样身份一次做完，实测落库（连续单库 `bt_baseA_cont.db`）：

| 身份 | 落点 | 实测值 |
|---|---|---|
| 参数指纹 `param_fingerprint` | `baseline.param_fingerprint` | `cc5f51e49a097640…`（param 表 `(key,value)` 排序序列 sha256） |
| `baseline_id` | `baseline.baseline_id` | `2026-11-04-newhigh-ladder-v1` |
| 引擎 hash `engine_sha256` | `baseline.engine_sha256` | `97edfc6b9603115b…`（`os.Executable()` sha256） |

**实施要点（0027 注释照录）**：modernc SQLite 无内置 sha256，且本工程未注册自定义 SQL 函数——
指纹/hash 必须在 **Go 侧**（`store.RecordBaseline()`，`crypto/sha256`）算，0027 只负责建 `baseline` 表
DDL。`params_json` 存参数快照，`latest=1` 标记最新一次重建；同库多次重建多行。

> 效果：两个库是不是同一基线，比一下指纹就知道（呼应 HARD①：跨二进制不可横比，必须先有身份才谈对账）。

**引擎常量的归属（docs/54 #4 拍板，2026-11-04）**：`box` 箱体确认 `ConfirmDays=3` **冻结为引擎常量，
不设 param 键**——少一个键少一份漂移。理由是它已被 `engine_sha256` 覆盖：改这个数必须改代码，
二进制 hash 必变，续跑/HARD① 立刻拒绝。三处生产构造（`scanner.boxParams`、`regime` 标定、
`cmd/darvas`）统一从 `box.DefaultParams()` 起手再覆盖可调字段，杜绝「漏填退化成零值」。
→ 后果：`docs/04 §9.3` 的 `box.period` 待办条目**作废**（不再参数化）。

## 五、永续化设计（F1/F2/F3/F5/F8 的补法）

### 5.1 目标态

**从"14 个单年库"升级为"一条连续单库"**：一条 2005→今 的账本，持仓跨年结转，复利是真实资金约束，
D 日之后能**日追加**，中断能**断点续跑**。

### 5.2 三个改造（按依赖顺序）

| 序 | 改造 | 补哪个缺口 | 落点 |
|---|---|---|---|
| **① 连续单库** | 去掉"每年 100 万起跑"，让 `from` 的初始权益 = 上一年年末权益 + 未平仓结转 | F1/F2 | `backtest.go` Bootstrap 加"结转"语义 |
| **② 断点续跑** | Bootstrap 加 `--resume`：从 `max(ok date)+1` 续，不清库 | F5 | `backtest.go` + `daily_run` 读断点 |
| **③ 日追加** | 回测产物支持 append D 日，而非整段重跑 | F3 | 回放链路加 append 入口 |

### 5.3 生产端 CatchUp 也要修（F8）

`CatchUp()` 现在只补前一交易日。要改成**从 `max(ok date)+1` 连续补到今日**，停机一周补 6 天，不留洞。
（`daily_run` 表的数据已经在，缺的是"多日循环补跑"的代码。）

### 5.4 断点续传的语义承诺

一旦 ① ② 落地，承诺：

- **幂等**：同一窗口重跑，产物全等（`daily_run` UNIQUE 兜底 + `equity_snapshot` 非空判据）。
- **可续**：中断后从断点续，不等同于"从头重跑"，也不丢已跑结果。
- **可对账**：断点前后账本连得上（靠 §四 的基线身份 + 参数指纹）。

## 五之二、新基线必须实现的两项特征（2026-11-03 用户拍板，重建前定死）

> 这是**业务特征**，不是工程补丁。它们和 §五 的永续化改造**并列**，都是"新基线建成"的硬标准——
> 缺任何一项，都不算"建成了新基线"。

### 特征一：DarvasBox 完整身份链（箱体生命周期可追溯）

用户要求：每个达瓦斯箱体必须能回答"**它是谁、何时生、何时破、何时死、卖在何时、跟谁相关**"。

**现状核实（照实说，代码实读 + 实库抽查）**：

| 身份要素 | 现状字段 | 状态 |
|---|---|---|
| 箱体 id | `box.id` | ✅ 已有 |
| 出生日期 | `box.bottom_confirmed`（下轨确认 = 箱体正式成立） | ✅ 已有 |
| 突破日期 | `box.broken_date` | ⚠️ 已有，但**向上突破与向下破位共用一列** |
| 死亡日期 | 无独立字段，靠 `box.status`（broken_up/broken_down/invalid）+ `broken_date` 隐式表达 | ❌ **缺显式语义** |
| 卖出日期 | `position.closed_date` | ✅ 已有 |
| 相关箱体 | `box.prev_box_id`（上一箱体） | ✅ 已有 |
| **箱体 ↔ 持仓关联** | `position.entry_box_id` | ⚠️ 历史库全 NULL（旧二进制旧产物）；**代码已修（T2 追踪链），重建即生效** |

**真正的缺口只有两处**，不是要重造一堆字段：

1. **「突破日期」与「死亡日期」语义未分离**：现在 `broken_date` 一个字段既记"向上突破"（新生命周期开始），
   又记"向下破位"（箱体作废）。要拆成：
   - `broken_date` → 保留为**向上突破日**（触发买入）；
   - 新增 `dead_date` → **死亡日**（向下破位 / 判 invalid 的那天），或复用 `status` + 显式 `dead_date`。
2. **`position.entry_box_id` 全 NULL（历史产物，代码已修，无需再接线）**：
   核实结论——追踪链**代码已修好**（`planner.go:757` T2 追踪链 + `ledger.applyBuy → reasonBoxID()` 会写
   `entry_box_id`，有 `TestTrackingChain` 端到端测试覆盖 `planner_test.go:1047`）。
   历史库 `bt_baseA_*` 全 NULL 是**旧二进制 + 旧 schema（停在迁移 0019）跑出来的旧产物**；
   **新基线重建后该字段自然有值，无需再改代码**。剩余动作只在重建时验证非 NULL 即可。

**落地（一次做完）**：

- 迁移：box 表加 `dead_date`（突破/死亡语义分离）。`entry_box_id` **不用再修**（已修好，重建即生效）。
- 语义承诺：**一个箱体的完整生命周期 = 出生（bottom_confirmed）→ 突破（broken_date）→
  死亡（dead_date）→ 卖出（position.closed_date）→ 继任（下一箱体 prev_box_id 指回它）**，
  全程可追、无需 `(code, top, bottom)` 兜底匹配。

**落地结果（2026-11-04，0028 + 0029；实库 bt_baseA_cont 跑到 2011-11-29 验收）**：

| 项 | 结果 |
|---|---|
| `dead_date` | 104,836 箱体：`broken_down` 57,046 全有值 / `invalid` 20,403 全有值 / `broken_up` 25,150 全空 / `forming`+`confirmed` 全空；5 条一致性断言 0 违规 |
| `entry_box_id` | **556/556 = 100% 非空**（旧库全 NULL 确为旧二进制产物，代码无需再改）；指向不存在箱体 0 笔、跨股票错配 0 笔 |
| `broken_date` 收紧 | 0028 首版仍双写（`broken_down` 两列同值 100%，占全部箱体 54.4%），0029 改为破位只写 `dead_date`；`BreadthAgg` 按状态取列，因旧库两列同值故聚合结果不变 |

**验收中发现并修复的第二处缺陷（原文未预见）**：`UpsertBoxes` 的身份键原为 `(top, bottom)`，
同价但不同生命周期的箱体会复用同一行，把买入当时的 `status`/`broken_date` 覆盖掉。
实测后果：**34 笔**持仓 `opened_date` 早于其箱体 `broken_date`（最多早 86 天）、**11 笔**买入挂在
`broken_down` 箱体上、`broken_date` 非空却非 `broken_up` 的箱体占 54.4%。
具体案例 sz000049：`signal` 2005-03-11 `breakout` 写 `box_id=49678`，该箱体现已是 `broken_down`、
`broken_date` 被改写为 2005-03-22，买入时的突破记录只剩死亡。
→ 0029 起身份键改为 **`(top, bottom, bottom_confirmed)`**（`invalid` 再追加 `dead_date`——
作废箱下轨未确认时身份会退化到只剩 `top`，实测 124 组撞键），
被 `position`/`watch`/`signal` 引用的旧行由 stale 逻辑永久保留，历史事实不再被重算改写；
回归测试 `TestUpsertBoxesIdentityStable` / `TestUpsertBoxesInvalidIdentity`。

残留缺口：仍无 append-only 生命周期事件账、无 `start_date`/`invalidated_date`，详见 docs/03 §2.1 注记。

### 特征二：牛熊识别 + 攻防转换（牛市加满 / 熊市撤退）

> 详见 `docs/48-regime-attack-defense-design.md`（已立项、B 类待跑）。本文只规定**它作为新基线特征的验收地位**。

用户要求：系统必须能**自动识别牛熊**，据此调节**牛市加满、熊市撤退**的总仓位。

**现状**：三个状态输入（MA60 闸门 / 个股距高阶梯 / A 判据）都在，但**没有一条线接到总仓位**——
升势日仓位 18.9% vs 震荡 15.1%，状态变了仓位只动 3.8pp；且 91% 时间被判"震荡"。
**缺的不是识别器，是传导**（48 §一）。

**已定设计（48 §四，跑前宪法）**：

- **L1 状态机**：市场宽度 b50（MA50 上方占比）+ 指数距高 dd52 双确认 → 进攻/中性/撤退，3 日滞回治 2018 洗耳光；
- **L2 目标暴露**：进攻 50~65% / 中性 20~30% / 撤退 5~10%；
- **L3 传导**：`planner.go` 单位乘数 ×2.0 / ×1.0 / ×0.5，**只动买入单位、不碰出场**（P2-6a 红线）。

**它作为新基线特征的验收地位**：

- B 类判据（48 §五）**全过 → 攻防转换进新基线**，`pos.regime_scale.*` 参数种子化；
- B 类任一不过 → 判"H2 不成立"登记，攻防转换**不进新基线**，但"自动识别牛熊"的**识别层仍保留**（宽度序列已有独立价值）。
- **与基线身份、永续化并列**：三项都完成，才算"新基线建成"。

> **⚠️ 判据基准必须重算（2026-11-04 拍板：改口径「新基线重算」）**：48 §五 判据里的
> 974,937（14 年 Σ已实现）、18.9%（进攻态仓位现状）、±600 元/年（噪声门槛）、35%（进攻态下限）

## 七、红线（重建时不许犯）

1. **同一二进制锚**：跨机/跨二进制不可横比。换二进制必须重跑全部账本并换 baseline id。
2. **参数只走 migration**：改默认值必须写 migration（0017 教训），禁止 `--set` 手改当事实源。
3. **回测串行、用 scratch 库**：禁并发，禁污染实时库心跳。
4. **除权只认 `dividend_event`**：价格反推会把跌停误判成除权（0022 已修，别再走回头路）。
5. **`tdx.root` 故意不入库**：机器相关路径，自动探测 D:/H:/I:，换机不静默失效。
6. **旧基线被淘汰直接扔**：不留当对照组（用户铁律）。
